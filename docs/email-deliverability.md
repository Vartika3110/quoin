# Why support@quoin.co.in lands in spam

**Diagnosed 23 November 2026.** Covers `TRU-05` in
`QUOIN_LAUNCH_READINESS.md`, which is about whether a customer who
writes to support can be answered — the answer turned out to be "yes,
but they may never see the reply".

The application sends no email at all: there is no mail library in
`package.json`, no SMTP anywhere in `src/`. This is entirely the Zoho
mailbox, and nothing here is a code change.

---

## What the DNS says today

| Record | State | What it means |
| --- | --- | --- |
| `MX` | `mx.zoho.in`, `mx2`, `mx3` | Receiving works. This is why replies arrive |
| `SPF` | **Missing** | No `v=spf1` record exists. The only root TXT is a `zoho-verification=` string |
| `DKIM` | **Missing** | Nothing at `zoho`, `zmail`, `default`, `s1`, `s2`, `dkim`, `mail`, `selector1`, `selector2` under `_domainkey` |
| `DMARC` | `p=quarantine` | Present, and **not yours**: `rua=mailto:dmarc_rua@onsecureserver.net` is GoDaddy's auto-created record |

Read those last three together, because that is the whole fault. DMARC
says *quarantine anything that fails authentication*. SPF and DKIM are
what a message authenticates **with**. Neither exists, so every message
fails, and Gmail does exactly what the domain told it to.

The registrar published the policy. Nobody published the two records
that let mail pass it.

---

## The fix, in order

### 1. SPF

A TXT record at the root (`@`) of `quoin.co.in`:

```
v=spf1 include:zoho.in ~all
```

`zoho.in` itself publishes `v=spf1 include:spf.zoho.in -all`, so that
include is the right one for Zoho's India datacentre. Start at `~all`
(softfail) rather than `-all`: if some forgotten sender exists, a
softfail marks it rather than rejecting it outright.

### 2. DKIM

Not a DNS-only step — the key has to be generated by Zoho first.

**Zoho Mail Admin → Domains → quoin.co.in → Email Configuration →
DKIM**, add a selector. Zoho produces a public key and the exact TXT
record to publish at `<selector>._domainkey.quoin.co.in`. Publish it,
then click Verify in Zoho.

### 3. Prove it before touching DMARC

Send to a Gmail address, open the message, **⋮ → Show original**:

```
SPF:   PASS
DKIM:  PASS
DMARC: PASS
```

All three, or the next step makes things worse rather than better.

### 4. Take the DMARC record back

Replace GoDaddy's at `_dmarc.quoin.co.in`:

```
v=DMARC1; p=quarantine; rua=mailto:dmarc@quoin.co.in; fo=1; adkim=r; aspf=r
```

`p=quarantine` stays — once SPF and DKIM pass, that is the setting that
stops anyone else sending as this domain. What changes is that the
reports come to you instead of to a vendor nobody here chose. Keep
alignment relaxed (`r`); Zoho's envelope sender aligns, and strict
alignment is a thing to tighten later from report data, not up front.

---

## Two things that undo all of it

- **Sending as `support@quoin.co.in` from a personal Gmail account**
  ("Send mail as") breaks DKIM alignment, because the message is signed
  by Google for a domain Google does not hold the key for. Send from
  Zoho's webmail, or from a client configured against Zoho's SMTP.
- **Impatience.** DNS caches, and a domain with no sending history
  earns its reputation over days. The first messages after the fix may
  still be filtered. That is not the fix failing.

---

## When the app does start sending

It does not today, and WhatsApp carries order notifications instead. If
that changes — an order confirmation by email, a password reset — the
sender will be a third party (Resend, SES, Postmark) and will need its
own `include:` in the SPF record and its own DKIM selector published.
Adding a sender without doing both puts the new mail straight into the
same hole this document exists to describe.

Quoin is three businesses, not one

Read from the reference design — and the reason the backend is shaped the way it is.

A single catalogue fronts three operations with almost nothing in common underneath. Treating them as one product is the failure mode this build is organised to avoid.

The decision everything hangs on

Four fulfilment types — modelled per product, never assumed.

Four different pricing units appear in a single row of the reference design: Per Visit, /sq.ft., Onwards, Per Pc. That rules out a single price column and a single checkout path.

FulfilmentMeaningExamplePromise
instantIn a dark store inside the serviceable radiusPaint, pendant light18 min
scheduledReal stock, delivered on a chosen dateCement, sanitaryware2–3 days
bookableConsumes a professional’s time slotSite visit, consultationSlot picked
made_to_orderCut or manufactured after orderingMarble slabs7 days

The 18‑minute promise is only true for one of the four. Marble and a site visit cannot honour it, and a header that implies otherwise turns every such order into a support ticket. Each product card now carries its own real promise, and the header is scoped with “on in‑stock items near you”.

Two more consequences that are cheap now and painful later: money is stored in paise as integers throughout, because float rupees accumulate error across tier pricing, GST and promos; and price is resolved by a pure function rather than stored, so the server at checkout and the optimistic client total cannot drift apart.

What is built

Three commits. Every claim below was verified, not assumed.

Storefront shell & home page

Mobile reproduces the reference design closely. Desktop is a genuine reflow — sticky top bar, left category rail, 4‑up banners, 5‑up product grid, bottom nav removed. Both layouts ship in one markup tree, toggled by CSS, so there is no hydration flash.

Two real bugs found and fixed here: .rail was unlayered CSS, which beats Tailwind’s @layer utilities — lg:grid was silently losing and the desktop grid never applied. And an apostrophe inside a CSS comment broke the PostCSS tokenizer outright.

Product detail — the buy box

Rendered from fulfilment × pricing unit rather than hand‑wired per product. Marble gets a length × width calculator with a 10% cutting allowance (trade practice for stone and tile); a site visit gets a slot picker and no quantity at all; paint gets variant chips and a stepper.

Verified in browser: 10 × 12 ft = 120 sq.ft. → 132 with allowance → 135 ordered (min 20, step 5). ₹149 × 135 = ₹20,115, save ₹5,400, Pro saves ₹2,025.

Backend module 1 — identity

Seven API routes: OTP request and verify, logout, /me, address CRUD, serviceability. Phone‑OTP auth over Postgres via Prisma, with one response envelope shape so the planned native client implements error handling once.

Not yet run end‑to‑end — there is no Postgres on the build machine. The routes are compile‑verified; the security‑critical logic underneath them is covered by tests.

Decisions worth challenging

Defensible, but they are judgement calls — push back if you disagree.

OTP security rests on limits, not on the hash

A six‑digit code is only 106 possibilities, so no hash function makes a stolen table hard to reverse. The real defences are a 5‑minute TTL, a per‑challenge attempt cap recorded before comparison so a dropped connection cannot farm free guesses, and a per‑phone request limit. Codes are HMAC’d and bound to the phone, so one number’s code cannot be replayed against another.

Rate limiting keys on the phone, not the IP

What is being controlled is outbound SMS spend and harassment of the number’s real owner. Both survive an IP change, so an IP‑keyed limit protects the wrong thing.

Serviceability resolves on coordinates, never pincodes

Pincodes straddle store radii. Using them would make the 18‑minute promise false for a predictable slice of customers on day one.

Sessions are JWTs, and cannot be revoked early

Stated plainly because it is a real tradeoff. Tier is therefore re‑read from the database wherever money depends on it — a cancelled Pro member must not keep trade pricing for the remaining life of their token.

Open — needs a decision

Each of these blocks work that is otherwise ready to start.

What is the margin rule on the Ozone catalogue?

The PDF carries MRPs only. The model has mrp, price and proPrice as separate fields; without a rule (“sell at MRP − 18%, Pro at MRP − 27%”) every product renders with zero discount.

GitHub repo name, and private or public?

Three commits are sitting on a local main. Pushing and deploying are outward‑facing, so both are waiting on an explicit go‑ahead. Private is the recommendation.

Where does the rest of the catalogue come from?

Ozone covers fittings — a real slice of Interiors and Premium Products. The reference design also leads with cement, marble, paint, lighting and services, none of which this PDF supplies.

Running it

Storefront needs no database; the API routes do.

npm install
npm run dev          # storefront on :3000, runs on fixture data
npm test             # 21 unit tests
npm run typecheck    # tsc --noEmit

For the API, copy .env.example to .env.local, point DATABASE_URL at Postgres, then:

npm run db:migrate
npm run db:seed      # three Delhi dark stores

In development, login codes are printed to the server log rather than sent by SMS. Production refuses to boot without SMS credentials, so that can never be the active sender on a deploy.
